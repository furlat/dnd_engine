# Native alternatives for observed feature/world integration corners

This is an escape-hatch appendix to `features-world.md`, not a cleanup backlog. The audit found no feature/world rule that requires abandoning native typed Bevy systems. The six cases below explain where copying Python's implementation shape is unnecessary or where an overly simple native translation would change observable behavior. Use an alternative only when the implementation encounters that corner. No Python changes, rule changes, performance claims or newly executed tests are proposed. Test references below were read as existing intent evidence; they were not rerun during this appendix.

## 1. Mutable future templates: preserve the effective action, not scattered mutation

**Witness.** `dnd/classes/sorcerer.py:1007–1131` installs Metamagic by modifying existing spell templates' alternative costs, target count/extra costs or range; it remembers exact modified UUIDs and clears those overrides on removal. `_on_spell_cast` consumes the root on CAST_SPELL Effect or cancellation from Execution, while declaration cancellation leaves it ready. Its owning action-template back-edge participates in vetoable progression removal.

**Hard corner.** A native port that treats templates as immutable authored definitions cannot reproduce this by changing the definition resource globally. A port that copies each `alt_*` field into unrelated grant components risks partial cleanup and loses the exact selected-execution versus installed-grant distinction. Neither obstacle requires preserving Python object mutation.

**Native option if needed.** Retain authored definitions as immutable data. Put the admitted mode and exact affected installed grant IDs on a typed `MetamagicActive` condition component; native effective-action systems combine a selected installed grant with that source-owned overlay. The selected cast retains its concrete costs/range/targets and active-root identity before execution. A native metamagic-consumption system removes the overlay through the admitted condition-removal path at the existing cast phase; it does not clear a running cast's already selected values. Progression removal still waits for active-root removal before removing its provider grant.

**Observable constraints.** The current source selects templates present when the root applies. Applying the overlay automatically to a newly installed spell while the root is active would expand behavior; do not make that an incidental consequence of a broad query. Multiple competing overlays and cleanup ordering also need exact source ownership, rather than clearing every alternative field indiscriminately.

**Evidence.** `tests/engine/test_content_recovery_behavior_semantics.py:379` asserts invalid declaration preserves Quickened, an interrupted committed cast spends bonus action and consumes Quickened, and the original template becomes action-cost again. `tests/progression/test_direct_sorcerer_progression.py:609` asserts vetoed root removal preserves level, capacities and root. These support a low-risk representation alternative when exact applicability, ownership and selected execution are preserved. They do not qualify admitting newly installed templates or arbitrary overlay stacking.

## 2. Injury annotations and residues: factual HP commitment does not select dispatcher mode

**Witness.** `dnd/body_responses.py:88–151` reads current injury resolution and owner placement, deposits residues, then returns `injury.with_updates(body_release=...)`. Root audit verified `dnd/entity.py:3583–3643` creates DamageAppliedEvent and uses ordinary phase advancement. Its returned annotation is accepted even though HP is already committed. This differs from explicit `publish_committed_phase` deep-working-view dispatch.

**Hard corner.** Converting every event named “Applied” into an immutable observer notification loses returned body-release evidence. Moving residue work after completion loses causal tile children and can read a later location/door state. Conversely, serializing every downstream observer behind injury annotation imposes an unnecessary universal dependency.

**Native option if needed.** Use a typed injury execution record with ordinary ordered mutable annotation dispatch. Body-response native systems read the canonical injury and the current owner inputs at their actual invocation boundary, build a typed release/deposit request, and retain the resulting admitted regions. Residue deposit systems update tile-owned memberships and contribution amounts; the injury continuation installs the accepted body-release annotation before the injury's completion/capture fence. Keep unrelated observation work independent only when its inputs and capture boundary permit it. Publication mode belongs to the explicit dispatch operation, not to a guessed category derived from a name or HP state.

**Observable constraints.** Only positive normal-HP injury releases material; temp-HP-only or fully immune packets do not. Physical packet damage selects the weapon wound pattern ahead of an elemental rider. Deposits retain support/propagation geometry, current residue identity, amount caps and provenance. Depositing a hazardous residue on an already occupied tile is inert until actual entry. Source reads owner placement when this handler runs; freezing it earlier than preceding reactive handlers is a behavioral change unless independently justified.

**Evidence.** `tests/engine/test_body_residues.py:75,95,137,162` assert normal-HP gating, mixed-packet pattern selection, persistent membership through lethal damage, capped accumulation and injury-causal tile facts. This is an essential integration mode distinction; a typed continuation is an alternative to blocking the producer, not permission to discard annotation or causal children.

## 3. Per-turn admission and trait markers: retain actual claim timing

**Witness.** `AreaCondition._admit_trigger` (`dnd/spatial/area_conditions.py:1264`) writes its target→causative-turn fence before invoking the processor. `MembershipAreaCondition._admit_trigger` (`memberships.py:164`) installs a continuous membership before that repeat gate. In contrast, `BonusDamageFeature._processor` (`monsters/traits.py:748`) appends dice then attempts to add an owner marker; reset is on the owner's TurnStart Effect. Smite (`classes/paladin.py:42`) spends an actor slot and writes event-context dedupe.

**Hard corner.** Native parallel application to different targets can double-spend shared slots/markers. A generic “once per turn” component updated at turn reset silently conflates these three different mechanisms. Copying nested closure wrappers is unnecessary, but moving the admission claim after a child result changes behavior too.

**Native option if needed.** Keep separate typed rule data and native systems: area exposure allowance keyed by condition, recipient and causative turn ID; exact continuous membership admission; actor bonus-damage marker membership; actor spell-slot resource and per-damage-event Smite-applied evidence. A queued area request claims allowance at the same point as the source, then owns its save/damage descendants. Trait and Smite systems serialize the shared actor claim while unrelated computation may proceed. With no causative turn identity, retain the source's unrestricted area-trigger behavior.

**Evidence and limits.** `tests/engine/test_gas_traps.py:116,139` assert appearance/entry/TurnStart share one allowance in the same turn and a walk across multiple cloud cells exposes once. `tests/engine/test_spatial_conditions.py:314` asserts exact lease continuity and membership completion before field completion. `tests/engine/test_content_recovery_behavior_semantics.py:190` asserts one appended Smite packet and exactly one consumed slot. `tests/manual/test_53_srd_monster_traits.py:412` checks bonus-damage eligibility, but does not qualify nested marker admission or cross-turn reactions.

**Possible defects, not accepted changes.** BonusDamage's named `once_per_turn` interval is implemented by a marker lasting until the owner's TurnStart, not the area fence's causative-turn identity. Its marker application can also be vetoed after extra damage is already appended. Those are concrete distinctions needing rule/fixture qualification before replacing the marker with an infallible atomic counter. The port can preserve the existing marker protocol with typed components; there is no demonstrated blocker requiring a rule rewrite.

## 4. Provisional material replacement: a single final-state command is insufficient

**Witness.** `SpatialCondition` admission records displaced old/new footprints, installs provisional incoming membership before subclass mechanics, then finalizes incumbents on success or restores displaced membership on incoming failure (`area_conditions.py:305–492,587–635`). Area application can publish light/terrain/sensory facts and nested occupant effects. This is more than replacing one material enum.

**Hard corner.** Deferred “despawn old, spawn new” commands lose veto/failure recovery and the state visible during reactive incoming application. Making all incoming work invisible until a final atomic swap also changes that intermediate visibility. A world-wide snapshot/rollback framework is unnecessary.

**Native option if needed.** Use a typed `SpatialReplacement` execution with the exact admitted cells, incumbent identities, old footprints and stage. Narrow native systems own overlapping-cell admission, provisional grid membership, incoming mechanics and incumbent finalization. The record retains only the displacement and source-owned state actually required for compensation. Re-query after nested children; reserve/conflict-order those cells and graph owners while the operation is pending. Compensation remains a domain-specific material operation, not a universal operation interpreter or arbitrary reverse event playback.

**Evidence.** `tests/engine/test_spatial_conditions.py:95,496` deliberately throws after `super()._apply` and asserts only the incumbent remains, original exact cells remain owned and movement cost is restored. `:1257` asserts overlapping Wet sources share one manifestation until the last lease releases. The first test proves final restoration, not every possible observer's provisional evidence or exception point. Preserve current visibility initially; hiding it needs a separate behavioral argument. This case is a genuine transactional integration corner, with an available native representation.

## 5. Shared restraint repair: completion work must be an explicit domain stage

**Witness.** `preserve_spatial_restraint` (`dnd/spatial/restraints.py:230`) is a global pre-completion callback. It inspects exact canonical causal parents, excludes an ending lease, distinguishes incoming standalone Restrained replacement, may create a new manifestation and attaches remaining leases to it. Escape actions belong to exact source UUIDs. This cannot be represented solely by an ordinary handler attached to the departing manifestation.

**Native option if needed.** Keep typed restraint leases, independently owned standalone manifestation and shared edges. The native condition-removal coordinator schedules a typed restraint-reconciliation system before completion, supplying the removal/application identity and canonical cause. That system queries the target's surviving restraint leases and submits replacement application only for the source case that requires it; the coordinator waits for acceptance, rebinds exact edges and then completes. Relevant-target indexes can replace a global callback scan, provided callbacks' domain timing and admitted conditions remain equivalent.

**Evidence and limits.** `tests/engine/test_jaw_traps.py:186,211` assert both source orderings, surviving restraint after one lease ends, restored movement only after final release and preservation of a preexisting independent standalone condition. `:244` distinguishes suppressed magical Web from active mundane Jaw. Replacing the manifestation with a bare reference count would lose tags, ownership, veto and replacement history; that is not a behavior-preserving escape hatch. Typed pre-completion reconciliation fits without retaining the Python callback registry shape.

## 6. Same-rule nested plate execution: use invocation-local output state

**Witness.** `PressurePlate._refresh_pressure/_send_output` (`dnd/spatial/triggers.py:58–82`) commits the new contact state before emitting outputs. The first selected pulse may activate a portal, causing nested departure and release of the same plate before the outer invocation emits its remaining authored pulses. The source explicitly preserves the selected pulse tuple despite that release.

**Native option if needed.** If synchronous same-system reentry is awkward, store a typed plate-output execution containing the selected links, cursor and causative event, separate from the current plate state component. Native pulse systems emit one link and wait for its required children; nested contact work can mutate the plate while the outer output execution retains its selection. Resumption continues the original list; it must not gate remaining pulses on the plate still being pressed. A release-triggered control intent retains its own owner and cause.

**Evidence and limits.** `tests/engine/test_pressure_plates.py:132` asserts nested portal transfer leaves the plate released and does not manufacture a stale duplicate press; it permits either no press facts or a true/false edge pair depending on actual handler order. It does not prove the multi-output continuation case. The existing small native mechanism probe addresses that corner; complete gameplay and capture still require qualification. Source control flow is a valid synchronous implementation, not a demonstrated defect. Continuation data is an optional escape hatch that preserves its rule when native execution is queued.

## Decision boundary

These alternatives preserve condition-specific compiled native systems and ordinary typed component/resource access. None requires a universal scripting ABI, boxed domain conditions or a rule interpreter. The mechanisms already proposed in the Bevy design can host them. An implementation should keep the simple direct native system where it works, use typed pending execution only for an actual dependency/reentry corner, and qualify the observable phase/ownership/evidence boundary rather than reproduce incidental Python registries or call-stack shape.
