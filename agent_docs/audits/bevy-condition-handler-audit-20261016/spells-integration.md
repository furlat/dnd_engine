# Spell integration audit — 2026-10-16

This closes the integration-site coverage left explicit in `spells.md`. No Python production/test changes or new probe were made. The work is a source-backed input to the Bevy port design, including narrow behavior-preserving alternatives only where a chosen integration mechanism encounters a demonstrated hard corner. This is not a cleanup sweep.

## Coverage boundary

Reviewed all **121 inventoried condition-construction sites**, **57 registration/direct-dispatch sites**, and **633 event/condition interaction-call sites**, grouped into **344 enclosing functions**. Source-defined condition and callback bodies reviewed in `spells.md` are reused as evidence; ordinary action/helper enclosing bodies were read in this wave. For routine phase advancement and event field updates, reviewed their enclosing control flow and classified the calls as plumbing; the mere existence of `phase_to` or `with_updates` is not a new interaction family. The coverage TSV records each of these 811 overlapping site rows, its enclosing function/span, classification and the corresponding report family.

Supplemental scanning of executable condition/handler/concentration attributes, finalization hooks, source-requirement methods, cost overrides, grant factories and pool selection found integration functions that the original call-name inventory does not capture. These **37 additional enclosing functions** are included in the TSV as supplemental function records. Important omissions from the original inventory were **Sunburst's `_finalize_aoe`**, **Daylight's overlapping darkness removal**, **Sleep/Color Spray target immunity and pool selection**, **Darkness's exact slot retention**, **repeat-action source validation**, and the **dynamic `zone_type(...)` wall construction** inside an already inventoried action. This is why constructor counts alone cannot establish coverage.

All spell condition/handler integration sites found by the inventory and this supplemental scan have a read classification. Pure metadata/catalog schema/decorator implementation, unrelated targeting algorithms and numerical damage balance are outside this audit's qualification scope. Source reading does not qualify native execution, error recovery or parallel scheduling; no parity or speedup result is claimed. The original `spells.md` inventory-only limitation is closed for these integration sites, not for arbitrary other spell behavior.

## I1 — Temporary save contributions require a nested execution scope

`CharmPerson._apply` (`enchantment.py:142-202`) installs temporary Wisdom-save advantage when the target is fighting the caster, invokes `saving_throw`, then removes the exact modifier before reading the displayed save bonus. `Sunburst._apply` (`evocation.py:2235-2270`), `_apply_sunbeam` (`3565-3586`) and `Blight._apply` (`necromancy.py:454-488`) similarly install Constitution disadvantage around one nested save. The latter three use `finally`; Charm Person's source path does not. The processor can publish child events whose handlers initiate further saves while the modifier remains installed.

**Actual dependency:** the originating save and its nested mechanics observe the temporary contribution until that logical save settles; post-save reads observe its removal. **Removable coupling:** a Python stack frame and raw target-global modifier bookkeeping need not survive in the port. Use typed save-scope data and exact modifier ownership, with a native exclusive save seam or a target/value claim that defers unrelated queued readers while allowing the required nested descendants. A private per-save bonus is **not automatically equivalent**: it must prove the source's nested visibility/inheritance policy. Do not silently eliminate a nested save's current access to that modifier, or leak it into unrelated queued saves. Handler input component conflict detection alone cannot enforce this semantic scope across yields.

Qualification: nested save launched by a roll/save handler, an unrelated queued save on the same target, source/target retirement and failure cleanup; assert effective modifier maps and displayed post-save bonuses at each boundary. The design's general context/claim mechanism supports a rewrite but has no such proof yet.

## I2 — Exact accepted receipts replace history scans, while accepted measures remain distinct

`Harm._apply` (`necromancy.py:2005-2046`) resolves damage with a normal-HP cap, then immediately searches `effect_event.get_children_events()` for an uncanceled **TakeDamageEvent COMPLETION** against its target. It uses that event's `final_damage` to decide whether to add `HarmSource` and how large its maximum-HP reduction is. This differs from Guardian (`conjuration.py:4581-4599`), which sums **DamageAppliedEvent.applied_damage** under specific ancestry filters. Neither scan can run before damage completes.

`MagicMissile._apply` (`evocation.py:655-698`) records the damage owner's returned actual amount. Healing actions (`4594-4935`, `transmutation.py:1955-1979`) first wait for the intercepted healing-roll result, then record returned actual healing. `MassHeal._apply` (`evocation.py:5059-5099`) computes a request from current missing HP and **shared cast pool**, receives actual healing, subtracts that actual amount from `self.healing_pool_remaining`, then removes named sensory conditions. Separate recipients still compete for one pool; completion order must not decide who receives the remaining amount. The source begins at 700 and does not reserve by requested healing here.

**Actual dependencies:** exact child acceptance/completion, selected damage/healing measure, deterministic shared-pool commitment and subsequent condition consequences. **Removable coupling:** global cursor windows and scanning all child versions. If the chosen queue boundary makes the existing immediate scan impossible, use typed per-request receipts carrying accepted amount, exact incoming/applied event handles, causal parent/application IDs and failure/cancellation outcome. Keeping a small synchronous owner seam is also valid. Guardian and Harm consume different fields; a universal “dealt” number would hide a semantic change. Keep cast/zone budget commitment ordered or prove a reservation/refund algorithm equivalent when healing/damage is reduced or canceled.

Qualification: damage cancellation, temporary HP, reduction, caps, nested same-source damage, healing suppression and near-exhausted Mass Heal/Guardian pools; assert the resulting source condition, pool and public amounts. Existing design broadly specifies receipts/dependencies; these concrete consumers are unqualified.

## I3 — Damage, movement and condition sequencing remains visible after child work

`Sunburst._apply` (`evocation.py:2296-2310`) and `_apply_sunbeam` (`3587-3596`) apply damage and then inspect `target.health.life_state` before blindness. Enqueue-only damage followed immediately by that check can blind a target that source mechanics would already have killed. `RayOfFrost`, `ShockingGrasp`, `GuidingBolt`, `ChillTouch` perform damage then condition application without that same explicit dead check; do not impose a uniform new gate. `ChillTouch` (`necromancy.py:330-367`) applies a caster tracker, applies target No Healing, then links it without checking either return; exact contribution admission is handled below those calls.

Telekinesis has an **explicit pre-completion native callback**: `_resolve_telekinetic_transfer.impact` (`transmutation.py:1679-1701`) is passed as `commit_forced_movement(..., on_landing=impact)`. It invokes two damage packets with `independent_resolution=True`, fall damage, a life-state check, then a Dex save and Prone admission. This callback captures caster, target, DC and effect origin. Its lifetime and required damage/life/save/condition descendants must settle before the landing owner completes. An `independent_resolution` argument does not imply the following death-dependent branch can run early.

`MistyStep._apply` (`conjuration.py:597-625`) records a cursor, commits position, resolves paid-entry retreats, then reports the **actual** caster position; it must not report the requested destination as final. Dimension Door (`4405-4452`) admits every traveler transfer before atomic position transfer, revalidates selection/destinations after nested admission, then settles entry retreats and individual transfer completion, retaining committed publication errors. `move_displaced` (`wall_constructions.py:497-515`) returns a Boolean derived from actual position after nested forced movement; wall activation consumes it immediately.

**Removable coupling:** callback stack capture and global cursor scans can become typed landing/entry work with exact request/receipt IDs. **Actual dependencies:** committed position/life state, child outcome, admission order, group-transfer atomicity and requested-versus-actual reporting. A single end-of-root barrier is too late for these intermediate branches.

## I4 — Compound condition admission policies differ; do not normalize them from success text

The integration sites use several genuinely different policies:

- **Checked admission:** Mage Armor checks returned condition admission (`abjuration.py:590-614`); Continual Flame checks return and `.applied` (`evocation.py:4520-4531`); zones such as Globe/Antimagic and most conjuration fields check activation before installing concentration links. Guardian/Feast also retire the newly created object if zone/lifetime activation fails (`conjuration.py:4663-4703,5036-5064`).
- **Applied-flag link:** Hold Person/Monster, Bane/Bless, Protection from Energy, Stoneskin, Shield of Faith, Guidance, most illusion buffs, Slow/Haste/Jump/Enhance/Enlarge and Necrotic Bless call admission, then read that exact condition's `.applied` before linking. `ensure_concentration` can run before or after save/effect/admission depending on the action. Queue translation must preserve those child boundaries and not read `.applied` immediately after submission.
- **Ignored child outcome:** Death Ward, Aid, Sanctuary, See Invisibility, True Seeing, Sleep, Color Spray, Command, Blindness/Deafness and several damage riders return success-facing status without checking child admission. Blur and Expeditious Retreat then call `add_linked_condition` without an explicit local applied check. These are source observations, not authorization to invent stronger all-or-nothing rules.
- **Transactional owner helper:** Resistance, Banishment, Longstrider, Barkskin, Fly, Shillelagh, Fire Shield and marker-backed repeated spells call `apply_owned_condition`. Its actual implementation (`dnd/actions.py:5160-5194`) prepares effect and concentration admission, cancels provisional work on admission failure, commits the exact sustain link and both memberships, then publishes while aggregating committed publication errors. This is stronger than a plain add-then-link sequence.

Freedom of Movement (`abjuration.py:2432-2455`) ignores the condition return, unregisters the named old escape action, then registers a new escape grant with the new condition UUID. Its action validates the named condition and actual nonmagical restraint before use, and pays five movement using a calculation that excludes exact restraint-owned speed caps (`2166-2325`). Preserve exact source/grant validation and receipt-backed payment in a rewrite; do not infer from registration alone that a rejected condition grants usable authority.

**Port design:** translate each explicit policy to typed owner admission requests/results and native graph systems. The helper is an appropriate small exclusive coordination seam or state machine with reservations; adding `Commands` for every insert and immediately proceeding does not implement provisional visibility, cancellation or linked admission. Status text alone is not proof that the effect was admitted. Which ignored outcomes should become clearer in product output is a separate behavior decision.

## I5 — Named condition and source validation is exact authored behavior, not a universal identity rule

Restoration helpers (`abjuration.py:1579-1622`) traverse names/tags in priority order. `_remove_first_condition_by_name` and `_remove_first_condition_by_tag` return the selected name without checking removal success, whereas exhaustion reduction checks the returned Boolean. Remove Curse traverses a captured list and appends selected names irrespective of removal result (`1816-1835`). Protection from Poison removes named Poisoned before adding its protection. Heal/Mass Heal remove named Blinded and Deafened after healing. Eat From Feast (`conjuration.py:4915-4937`) waits for benefit-source admission, then removes captured disease/poison/fear memberships, updates `consumed_by`, and retires at zero charges; its finite item charge/action cost owner is the common action path, not a hand-coded decrement here. Concurrent servings conflict on item charges and guest/once-per-user sets.

Repeat-source checks also differ. Call Lightning Strike checks exact UUID membership before delegating (`conjuration.py:207-214`); Sunbeam Strike and Telekinesis Move explicitly require `.applied` and `contributions_active()` (`evocation.py:3639-3657`; `transmutation.py:1750-1783`). Eyebite checks named Concentrating with an Eyebite slot, then the exact typed casting marker and its successful-save target set (`necromancy.py:1345-1496`); it re-resolves marker state after save/effect work. Banishment (`abjuration.py:1554-1559`) skips later applications when its exact cast concentration UUID has disappeared. These are policies of the concrete call sites; replacing them all with “source entity exists” or “any condition of that type exists” is wrong.

Use domain lookup indexes and typed membership/source components, with exact admitted operation IDs when suspending. Hardcoded source names can become authored typed keys while retaining their priority/selection behavior. Private implementation naming is removable; changing which condition is selected or whether vetoed removal is counted is a behavior change requiring qualification. For source checks missing an explicit gate, evaluate the complete existing caller/contribution-owner path before strengthening it.

## I6 — Selected execution and cast state cannot live in one worker's system-local variables

Call Lightning/Sunbeam (`conjuration.py:262-282`; `evocation.py:3689-3708`) build exact marker and repeat-action identities, assign the marker's action UUID, admit ownership, clean the unregistered strike on rejection, register it on success, then resolve initial applications. Telekinesis similarly reserves a repeat UUID before marker admission (`transmutation.py:1828-1848`). Eyebite (`necromancy.py:1535-1580`) applies marker, links concentration, registers a repeat, and invokes the first strike's `_apply` directly inside the already-paid cast. Do not charge this first application as another standalone action or erase its exact marker origin.

Darkness `_retain_active_concentration_slot` (`conjuration.py:2845-2870`) writes the exact selected slot on the execution **and** its matching registered Entity-owned template by UUID. This is intentional durable state used by its later item/slot interactions, not evidence that execution and template can be one entity. `dnd/core/base_actions.py:2111-2155` currently mutates `self.target_entity_uuid` per application and restores it in `finally`; queued applications must carry distinct target/application IDs while preserving cast-owned mutable state separately. The same selected invocation holds `cast_concentrating_uuid`, pool state, retained origins and optional device owner. Parallel work cannot share one mutable “current target” field.

Sleep and Color Spray (`enchantment.py:948-1009`; `illusion.py:730-783`) filter condition/origin immunity and current capability/HP, sort `(hp,uuid)`, draw one pool, consume it during selection, cache the chosen target list, and return copies on subsequent calls. Recomputing target selection for each queued application would spend different pools and observe later HP/immunity. Mass Heal instead decrements a live accepted-healing pool per application (I2); these are not the same selection policy.

Ice Knife (`ice_knife.py:75-167`) freezes its burst center **before** initial attack/damage, then opens a nested cold `spell_execution_scope` binding the **same original cast lineage**. Burst target/application events get distinct IDs; one cold roll is shared; each save/damage acceptance precedes its application completion and root burst total. `dnd/core/spell_execution.py:47-95` resets context on leaving the Python scope. Port requests need explicit inherited source/type/cause/save context and lineage ownership across yields; creating a second cast lineage for the burst would duplicate once-per-cast claims. A global current-cast resource or worker-local state cannot represent overlapping pending roots safely.

## I7 — Reposts and pre-completion area finalization are executable behavior

Web/Entangle and Bestow Curse use `.post(...)` after their first Effect publication (`conjuration.py:1265,1473`; `necromancy.py:2549`), which may invoke same-phase handlers again under the established dispatch protocol. `with_updates` has distinct version/update semantics; it cannot be used as an interchangeable spelling for repost. Web additionally emits a zone state change after item-owned sustain linkage before returning the reposted spell fact.

The source explicitly calls `_finalize_aoe` **after all per-target applications and before root Completion** (`dnd/core/base_actions.py:2102-2109`). Concrete hooks read here:

- Fireball (`evocation.py:915`) deposits ASHEN_RESIDUE over the recorded reached footprint.
- Burning Hands/Lightning Bolt (`1161,1310`) ignite recorded cells excluding current spell-protection positions.
- Sunburst (`2328`) scans current spatial owners and deactivates overlapping spell-origin magical darkness.
- Gust (`3269`) activates its maintained zone; Ice Storm (`3478`) activates recorded-footprint terrain with source-turn expiry.

Daylight separately removes overlapping `DarknessZone` owners immediately after its own zone admission (`conjuration.py:3011-3024,3145-3157`), then links sustain; its reported removal count increments on attempted deactivation without testing the Boolean. Fireball's staged application body (`evocation.py:920-1045`) additionally observes parent cancellation, shared protection providers, support-parent ordering, actual object breakability and propagation revision; it completes each reach stage before deriving prerequisite destruction evidence and deciding the next stage.

These are **actual rule dependencies** on admission, committed spatial state, shared providers and prior applications. They may be represented by queued native jobs; their root/phase/completion fences must retain exact ordering. Their scans and stack hooks are **removable implementation coupling**: typed spatial requests and exact owner/result IDs are suitable replacements. “Routine phase plumbing” means the call site introduces no additional rule beyond the already audited event protocol; it does not mean publication can be elided or allowed to complete before these hooks.

## I8 — Silence alias classification after checking source/tests

The earlier report correctly identified `zone_positions = self.affected_positions` (`illusion.py:1306`) as a retained set-object alias. Base spatial footprint commitment replaces the set (`dnd/spatial/area_conditions.py:636-662`), so the blocker and current zone can disagree after that path. However, the Silence source describes an **established fixed origin** (`illusion.py:1274`), and the current manual regression (`tests/manual/test_134_cleric_batch1_legacy_contract.py:691-760`) checks verbal/nonverbal casting, overlapping Deafened ownership and cleanup, without asserting stale blocking after footprint replacement. The searched engine/manual Silence tests supplied no movement/footprint-change witness.

Therefore classify stale captured footprint as **legacy coupling / behavior ambiguity**, not a mandatory game rule to copy. No integration blocker is established for supported fixed-origin Silence, and a latent base footprint-change method does not create a requirement to support movable Silence. Retain the supported stationary blocking, overlap/removal and suppression behavior. If an actually supported mutation path is later shown to cross this alias boundary, qualify that exact path before choosing captured or authoritative footprint access. Before deciding an exact freeze/current policy for a related handler, inspect its actual capture and allowed mutation paths; a universal freeze or universal live-query substitution is unjustified. No Python defect was fixed here, and no unsupported claim is made that tests establish the changed-footprint outcome.

## Design consequences and remaining qualification

The reviewed integration does not require a domain OOP layer. Native systems can query typed actor/condition/value data, retain pending application/scope/landing records and use narrow exclusive seams for coupled admission/commitment. Where a chosen asynchronous implementation actually crosses the concrete boundaries above, exact receipts, application data and operation-owned state are narrow alternatives to history scans, transient current-target mutation and stack-lifetime guards. They are not a reason to rewrite otherwise compatible handlers in advance. It must retain actual save/result dependencies, nested scope visibility, exact source/slot ownership, cast pools, semantic update/repost distinctions and before-Completion owner hooks.

Recommended narrow proofs added by this wave: temporary save contribution with nested/unrelated saves; Harm receipt versus Guardian receipt; Mass Heal actual-healing pool; Sunbeam damage/death-before-blindness; Telekinesis landing hook ordering; exact marker/template retention and first-strike cost; Sleep/Color Spray selection-cache lifetime; area finalization before root completion. These complement the earlier Guardian/Gust/Antimagic/shared graph proofs. No executable Bevy qualification or measured scheduling independence is claimed by this source audit.
