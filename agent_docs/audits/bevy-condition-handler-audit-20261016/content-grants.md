# Permanent grants and extension audit — 2026-10-16

Read-only production audit; only this report and its coverage ledger were written. Scope is `dnd/content/characters/{origin_grants,barbarian_grants,fighter_grants,sorcerer_grants}.py` and `dnd/extensions/{aegis_spark,field_focus}.py`. Actual installer/remover/reconciliation implementations were read, including callbacks installed indirectly by factories. Native translation/probe qualification was not performed.

## Coverage reconciliation

The six assigned files total 5,009 lines. All executable grant bodies, extension class bodies and directly selected callback bodies were inspected; imports/data tables are support, not gameplay proof. [content-grants.coverage.tsv](content-grants.coverage.tsv) enumerates **every inventory row in these six files**, with reviewed status per site. Inventory contains 3 condition classes/4 condition methods, 7 direct handler constructors/7 processor arguments, 8 contextual constructors/8 callable arguments, 16 registrations/direct dispatch rows, 18 interaction calls, and 2 condition constructions. Loops and shared helpers mean site counts are not runtime instance counts.

The AST inventory omits indirect constructors behind helper factories: origin Hellish Rebuke; fighter Protection/Indomitable/Survivor; barbarian Indomitable Might/Retaliation; sorcerer learned Shield/Counterspell. These installations and their callback bodies were traced. The permanent installers themselves do not subclass BaseCondition; mapping all gameplay contributions from condition-class counts would miss them.

Supporting source inspected: named functions in classes/fighter.py, classes/barbarian.py, classes/feats.py; origins/halfling.py and half_orc.py processors (including natural-d20 helper); infernal.py Hellish Rebuke processor/factory; reaction_spell_content.py factory/spec linkage; abjuration.py Shield/Counterspell processors/factories and Counterspell completion; spellcasting.py learned reaction-source add/query/remove methods. **Not reviewed completely:** those larger supporting modules, action implementations for every granted template (SecondWind, Rage/Frenzy, Dragonborn breath, metamagic etc.), progression resolvers/receipt dataclass schemas, action-resource capacity/recovery implementations, entity action unregistration semantics and external command serialization. Their calls are identified below, not claimed fully qualified here.

- aegis_spark.py:16 AegisSparkEffect installs one exact +AC ID before Effect and returns ownership; no custom runtime hook. :135 AegisTrainingFeature **unregisters by action name then registers new template during _apply** (:164–176); only _remove :179 cleans it up. ## Design comparison and necessary proofs

**Covered conceptually, unproven:** existing design §§14/20 already permits live contextual processors, typed permanent receipts/source sets, actor-owned resource data and concrete systems. No impossibility of native Bevy translation was found. It needs the following concrete cases before claiming these factories/conditions covered:

1. Shared learned reactions across two sources: add/remove one, last-source removal, disabled-but-retained displaced handler, restore prior UUID/enabled state, stable dispatch rank and source-option order. Include Hellish Rebuke innate versus ordinary source cost/DC selection and Counterspell best-ability selection.
2. Exact ordered template displacement: Rage→Frenzy and delevel restore UUID/list position/config; active Rage removal veto; delevel of a later feature ends earlier-owned root when configuration changes. Sorcerer replaced ordinary spell regains index; unrelated same-spell template from another source survives level update/removal.
3. Receipt ownership mismatch: stale handle/local-versus-queue discrepancy rejects removal before teardown; exact source removals preserve sibling feature/proficiency/resource claims. Qualify partial installer failure compensation and current unprotected reconciliation numeric writes separately; do not promise one universal transactional undo.
4. Multiple value owners sharing one modifier identity: Fast Movement and Field Focus all-speed insertion, suppression/evaluation and exact cleanup. Query systems may read live armor/weapons/abilities and return invocation-specific explanation evidence; installation snapshots are insufficient.
5. Interceptor order/resource/random evidence: Halfling Lucky versus Lucky; Relentless Endurance versus Relentless Rage damage caps; Protection's nested numeric mutation; Indomitable nested roll before payment; Retaliation's complete nested attack; Survivor nested healing. Disjoint targets alone do not establish source-pool/handler independence.

**Missing explicit source exceptions / potential semantic changes:** the proposal's broad condition cancellation/rollback and atomic replacement descriptions do not enumerate AegisTraining's provisional action-registry mutation, AegisSpark's manual early remove, or action success after ignored child cancellation (AegisSpark, FieldFocus, Shield). A port must preserve these observable paths or explicitly approve a gameplay correction; an accepted child dependency does not imply the caller presently checks success. These are source behaviors, not recommendations to perpetuate defects. No silent fix belongs in an architecture feasibility claim.

AntiOOP exposure: native typed components for installed grant/source receipt, ordered action identity, source-set reaction ownership, exact value-map handles and per-rule configuration; concrete Query/SystemParam processors for current equipment/ability/senses/resources; explicit ordinary progression/removal systems that own their existing validation and compensation. Stable domain IDs remain independent of native Entity storage lifetime. Avoid `dyn CharacterClass`/`dyn Feature` actor objects, a generic effect/grant interpreter, reflection-based owner routing, or a blanket hierarchy/despawn policy. Queue only when these exact pending claims and source updates have a defined boundary; initially sequential progression and ordered interception are legitimate, while pure invocation-owned arithmetic may run independently after input ownership is established.
